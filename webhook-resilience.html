Preloop control plane · webhook resilience

What if GitHub doesn't deliver?

GitHub sends each webhook once and never auto-retries a failure. Preloop answers 202 only after the raw delivery is committed to the durable queue. Everything after that is our problem — and our repair surface. This page maps each failure to its flow and fix.

How to read these diagrams

violet — GitHub side (event, delivery history, REST API).
cyan — ingress / HTTP boundary (Funnel, proxy, 202/500).
amber — durable store (webhook_deliveries). The only thing GitHub's 202 is allowed to mean.
green — background worker (leases, retries, checks).
red dashed — the failure edge. Everything left of it exists; everything right of it never happened.

Ground rules (already true)

✦  Enqueue budget: 8s, 2 attempts — then 500, never a hung GitHub connection.
✦  Processing retry: 1s → 5s → 15s → 30s, max 6 attempts, 60s lease / 20s heartbeat.
✦  Redelivery key: X-GitHub-Delivery GUID — active/done dedup, failed rows reopen.
✦  Payload ceiling: 32 MiB (above GitHub's 25 MiB) so real deliveries get a verdict, not a reset.

Why this ordering matters

  • GitHub's 10s / 2xx rule means slow synchronous processing = recorded failure.
  • A 202 before commit would be a lie: GitHub won't resend, and we'd have no copy.
  • Duplicates (GitHub double-fire, redelivery) return 202 duplicate, no second run number.

Already handled

  • Duplicate GUIDs deduplicate before run-number allocation.
  • Replayed payloads reuse the run and PATCH the existing check instead of POSTing a second.
  • Crash between run creation and done is at-least-once + idempotent, not exactly-once.

If we got this wrong

  • Returning 202 without a commit deletes the only copy: GitHub won't resend, we have nothing queued. Silent CI dark.
  • Hanging past 10s is the same as a 500, minus the clear log line.

Correct handling

What breaks without this

  • A blip in contents / commits / PR-files APIs would dead-letter a good push.
  • Two workers could double-submit a long workflow fetch without lease renewal + fencing.

Why polling is required

  • GitHub never retries on its own — a dead host is just a red row in Recent deliveries.
  • The 3-day history is the only other copy of a delivery that never reached us.
  • Poll cadence must stay well inside 3 days with a persisted watermark.

Proposed watchdog

  • List ?status=failure, fetch full payload via delivery id, redeliver only when local store is healthy.
  • Per-delivery backoff; re-check status after each redelivery (the API only schedules an attempt).
  • Alert when last successful poll goes stale — a blind watchdog is worse than none.

Why this is the scary one

Traps

  • Treating “no webhook in 30s” as lost creates duplicate runs when the real one lands late.

  • Watchdog waits out a grace window, checks delivered_at / throttled_at.

  • Source-state repair (scenario 07) runs after the grace window, with idempotency keys.

Current gap

  • GitHub-dependency errors are transient, but the queue caps at 6 attempts — a 30-minute GitHub incident can dead-letter good pushes.
  • Every queued delivery would hammer GitHub independently during recovery.

Correct handling

  • Split taxonomy: bad payload → dead-letter fast; GitHub unavailable → park long.
  • One shared breaker pauses GitHub-dependent claims; watermark never advances on failed polls.
  • Respect rate-limit headers; back off globally, not per-row.

The race to avoid

  • Reconciler creates a run at T+5m; the delayed real webhook lands at T+6m with a different GUID → duplicate run + duplicate checks.
  • Delivery-ID dedup alone can't catch this — the synthetic run has no delivery ID.

Correct handling

  • Idempotency key: repo + event + ref/PR + workflow path + head SHA, persisted durably.
  • Feed synthesis through the same event adapters as webhooks (dispatch.rs pattern).
  • Accept approximation: REST state can't rebuild multi-commit pushes or action-specific PR semantics exactly.

What each layer cannot do

  • Watchdog can't fix events with no delivery record — needs layer 4.
  • State repair can't replay exact history — the delivery payload stays authoritative.
  • Neither helps while GitHub is fully down — retain watermark, retry, don't advance.

Deliberately out of scope here

  • HA ingress gateway: second durable queue buys host-downtime 2xx, costs another failure domain. Build only if “ack while Preloop is down” is required.
  • Active-active Preloop: instances diverge in memory today — needs shared-bus refactor first.
