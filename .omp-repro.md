## Goal
Memory-bound hardening (Medium) for authenticated-runner memory-exhaustion. Fix each sink so it is capped/bounded without breaking protocol fidelity. 6 findings remain open — F4 (live logs) already shipped via PR #148.

## Background
A malicious authenticated runner (RunnerListen JWT or `Actions.Results:{plan}:{job}` runtime token) can exhaust server memory over many `200 OK` requests. Per-request Axum `DefaultBodyLimit` (2 MiB default; explicit 64/32/512 MiB on /api/v1/runs, /api/v1/github/webhooks, /twirp-blob) already exists — the real hole is state that grows unbounded across many requests inside `Arc<Mutex<InnerState>>`.

## Findings to fix (6 OPEN, verified against origin/main line numbers)

### F1 — logs: `BTreeMap<String, Vec<u8>>`
- `crates/preloop-runner-server/src/state.rs:1159` `pub(crate) logs: BTreeMap<String, Vec<u8>>`
- `crates/preloop-runner-server/src/timeline_logs.rs` `append_log(body: Bytes)` + `create_log` — `inner.logs[plan/logId].extend_from_slice(&body)` no cap
- Auth: `require_protocol_bearer` — runner/job JWT. Repro: 100*64KiB appends → single Vec 6.5MiB; +50*1MiB distinct keys → ~56MiB total.
- Fix: MAX_LOG_BYTES 16MiB per key + MAX_PLAN_LOG_BYTES 64MiB total → 413/truncate; evict oldest plan.

### F2+F3 — timeline_records + timeline_events
- `state.rs:1166` `timeline_records: BTreeMap<String, BTreeMap<Uuid, TimelineRecord>>`
- `state.rs:1161` `timeline_events: BTreeMap<RunId, Vec<NdjsonEvent>>`
- `timeline_logs.rs` `patch_timeline_records` — `stored.insert(record.id, record)` + `.extend(projected)`. 2000 distinct ids → records=2000, changeId=2000.
- Fix: MAX_RECORDS 1024 per timeline; ring buffer 2048 events per RunId.

### F5 — blob blocklist assembly `Vec<u8>`
- `crates/preloop-runner-server/src/blob_store.rs:89-93` `let mut assembled: Vec<u8> = Vec::new(); ... assembled.extend_from_slice(&read(block))` then `write(data, &assembled)`
- Auth: job token (results bearer), `PUT /twirp-blob/:kind/:token?comp=block{,list}` (512 MiB BodyLimit). Repro: 20*1MiB staged → blocklist XML → single 20MiB Vec at once; 512 blocks → OOM.
- Fix: reject `block_ids.len() > 10000` or total > 512MiB; stream copy chunked (tokio::fs::File + copy), never Vec of full size; per-block 4MiB cap.

### F6 — GET timeline amplification, no pagination
- `timeline_logs.rs` `get_timeline_records` / `get_timeline_records_plan` — `stored.values().cloned().collect()` → `Json({count, value})` clones full timeline.
- Fix: `?top=$top` with MAX_TOP 500 server-side, paginate otherwise.

### F7 — artifact/cache v2 pending maps unbounded
- `state.rs:1191` `artifact_v2_pending: BTreeMap<String, ArtifactV2Pending>`; also `cache_v2_pending`, `cache_v2_dl_tokens`, `artifact_v2_registry`
- `artifact_twirp.rs` `twirp_artifact_v2_create` → `inner.artifact_v2_pending.insert(token, ...)` no per-job limit.
- Fix: MAX_PENDING 32 per job + TTL sweeper (same for cache_v2).

## Already-shipped pattern to mirror — F4 live logs (PR #148, on main)

- accounting covers wrapper struct + step_id + every line string capacity
- durable step-log blob remains source of truth for full logs
- unit tests for tail-drop eviction, oversized-wrapper rejection, snapshot cloning
This is the in-repo convention for a memory cap. Use the same style.
