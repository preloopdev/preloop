aksh Concurrency State Machine

Full lifecycle trace: Submit → Park → Release → Promote → Cancel

0. What's a holder?

A holder is whoever claims or waits for a slot in a concurrency group. Three kinds, matching GitHub's three scopes:

Run Workflow-level

The whole run claims the slot. Every job inside shares it.

concurrency: group: deploy-prod

All jobs park together, release together.

Job Job-level

Each individual job claims the slot independently.

job-a: concurrency: group: deploy-prod

Jobs from different runs interleave in the FIFO queue.

JobSet Reusable workflow (multi-gate)

A reusable workflow call via uses: that carries its own concurrency: block. Must acquire all gates atomically — partial admission would deadlock.

call-tests: uses: ./.github/workflows/run-tests.yml concurrency: group: shared-gate

Two gates: the caller's group + the embedded group. Both must be free.

2. Parked — what Ok(false) means on the inside

When try_acquire_concurrency returns Ok(false), the holder is parked. This ripples through the run:

// For a Run holder: statuses.insert(job.job_id, "Pending"); concurrency_blocked.push_back(job); // The run's status becomes Pending, not Queued run.status = summarize_run(run.jobs.values()); // → Pending

The jobs sit in concurrency_blocked — they're not in the scheduler queue, no runner will pick them up. They're frozen until the holder gets promoted.

3. Release — leaving the club

When all jobs in a run finish (or a job finishes for job-level), the server calls release_concurrency_for_run or release_concurrency_for_job.

    KEYS --> EACHKEY["For each key:"]

4. Promote — letting the next person in

promote_next_from_group is the heart of the FIFO queue. It pops the next pending holder and dispatches it based on kind:

sequenceDiagram
    participant G as ConcurrencyGroup
    participant P as promote_next_from_group
    participant H as held_runs / concurrency_blocked
    participant Q as Scheduler Queue

    G->>P: pop_front() → next holder
    P->>P: match next.kind

    alt Run holder
        P->>H: held_runs.remove(run_id) → [jobs]
        H->>P: for each job: under_max_parallel?
        P->>Q: push_back(job) ← runners pick it up
        P->>G: group.running = Run(next)

    else Job holder
        P->>H: concurrency_blocked.pop(job)
        P->>P: under_max_parallel(inner, &job)?
        alt full
            P->>G: push_front back to pending ← retry later
        else free
            P->>Q: push_back(job)
            P->>G: group.running = Job(next)
        end

    else JobSet holder
        P->>P: advance_jobset_admission(id, promoted_key)
        loop for each unacquired gate
            P->>G: try_acquire_concurrency(gate.key)
            alt blocked
                P->>G: stay pending ← wait
            else overflow
                P->>P: release_jobset_admission → clean partial keys
            end
        end
        P->>H: drain concurrency_blocked → queue all jobs
        P->>Q: push_back(all jobs)
    end

Continuing the trace: Run(A) finishes

StepActionrunningpendingholder_keys
4Run(A) completesRun(C)[]C→{deploy}
5Run(C) completes—[]{}

At step 4, promote_next_from_group pops Run(C) from pending, installs it as running (Run holders go straight in), then finds held_runs[Run(C)] and injects all its jobs into the scheduler queue. Runners see them and pick them up.

At step 5, the group is empty. cleanup_group removes it from concurrency_groups.

5. Cancel — cutting the line

Two things trigger cancellation:

  • cancel-run API call — user manually cancels a run
  • cancel_in_progress — a new arrival with CIP=true kicks the current holder
fn cancel_holder(inner, holder, reason) { match holder { // Run: cancel every job, mark run Cancelled Holder::Run(run_id) => cancel_run_inner(inner, run_id), // Job: cancel just that job Holder::Job { run_id, job_id } => cancel_job_inner(inner, run_id, job_id), // JobSet: cancel all jobs + release all partially-acquired gates Holder::JobSet { run_id, job_ids } => { release_jobset_admission(inner, id); // ← clean up keys! for job_id in job_ids { cancel_job_inner(inner, run_id, job_id); } } } }

6. Side-by-side comparison

Run

One holder for the whole run.

  • Jobs submit together, release together
  • Simple FIFO: one run at a time
  • No interleaving with other runs
  • Release: release_concurrency_for_run
    → look up keys from holder_keys

Job

One holder per individual job.

  • Jobs from different runs interleave in FIFO
  • Max-parallel check before dispatch
  • If max-parallel full → push back to front of pending, retry later
  • Release: release_concurrency_for_job
    → scans all groups for this job

JobSet

One holder for a reusable workflow call with embedded concurrency.

  • Must acquire N gates atomically (caller + embedded groups)
  • Partial admission tracked in jobset_admissions
  • If any gate blocks → park entire set, keep acquired keys
  • If promoted again → resume from last unacquired gate
  • If any gate overflows → release_jobset_admission cleans up all partially-acquired keys
  • Once all gates ready → all jobs go to scheduler at once

8. The critical detail: holder_keys

holder_keys: BTreeMap<RunId, Vec<(String, String)>> is the reverse map. For every run, what groups does it occupy?

This is what makes multi-key cleanup reliable:

// When releasing a JobSet that acquired 2 keys: holder_keys[Run(F)] = [("repo-a","deploy-prod"), ("repo-a","shared-tests")] // release_concurrency_for_run iterates holder_keys[Run(F)]: for key in holder_keys[Run(F)]: promote_next_from_group(inner, &key, done); // Without holder_keys, you'd have to scan EVERY group to find where this run is — O(n) per release. // With holder_keys, it's O(k) where k = number of groups this run actually occupies.

Without this, a JobSet that got through gate A but blocked on gate B would leave a ghost entry in gate A — the next queued run would never be promoted because the group still thinks the JobSet is running.
