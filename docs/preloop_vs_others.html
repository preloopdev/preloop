Three ways to run GitHub Actions locally

nektos/act · agent-ci · preloop — and Gitea Actions (act_runner). Both let you run GitHub Actions workflows locally. They take fundamentally different approaches to the problem.

02 // ARCHITECTURE

act — a monolithic Go binary

┌──────────────────────────────────────┐
│            act (Go binary)          │
│  YAML parser → Planner → Executor   │
│  Expression evaluator · DAG sort    │
└──────────────────┬──────────────────┘
                   │ Docker API
        ┌──────────▼──────────┐
        │ Job container        │ ← tail -f /dev/null keeps it alive
        │ (ubuntu image)       │ ← steps run via `docker exec`
        │ + service containers │ ← same Docker network
        └──────────────────────┘
  • Language: Go 1.24+ · single static binary (~8 MB)
  • Execution: monolithic — parses, plans, and executes in one process
  • Container model: one long-lived Docker container per job, entrypoint `tail -f /dev/null`, steps via `docker exec`
  • Host mode: `-self-hosted` runs steps directly on the host

preloop — a Rust control plane + runner

┌──────────────────────────────────────┐
│    preloop-runner-server (Rust, Axum)   │
│  YAML parser → Scheduler → AzDO wire │
│  expressions · concurrency groups    │
│  cache/artifacts · OIDC · DAP debug  │
└──────────────┬───────────────────────┘
               │ AzDO protocol (HTTP/WS)
     ┌─────────┼──────────────┐
┌────▼───┐ ┌────▼───┐  ┌─────▼────┐
│Official│ │ preloop-  │  │ SmolVM   │
│actions/│ │ runner │  │ (libkrun │
│runner  │ │ (Rust) │  │  microVM)│
└────────┘ └────────┘  └──────────┘
  • Language: Rust — server (axum) and runner (Listener + Worker)
  • Execution: client–server over the official AzDO wire protocol, verified against golden captures of runner v2.336.0
  • Container model: one isolated microVM per job (smolvm/libkrun); the unmodified official runner also works against preloop

04 // EXECUTION MODEL

  • act keeps one idle Docker container alive per job and runs every step through `docker exec` on your host kernel — fast, but a step can see the host's kernel and any shared Docker daemon state.
  • preloop builds the job on the server, ships it to a runner over the AzDO wire protocol, and executes it inside a dedicated smolvm microVM — separate kernel, network off by default, per-job lifecycle.
  • Gitea Actions reuses act's execution engine but the Gitea monolith does scheduling (needs/matrix/concurrency) and ships the workflow YAML to the runner over proprietary Connect RPC.

05 // PROTOCOL FIDELITY

act — no protocol

act parses the YAML itself and executes steps. Nothing speaks the runner protocol, so nothing can be verified against GitHub's actual behavior — discrepancies surface when your workflow fails.

preloop — full AzDO wire protocol

  • Registration: RSA key exchange, runner capabilities, labels
  • Session: AES-encrypted message queue, session renewal, conflict resolution
  • Broker: acquirejob → renewjob → completejob lifecycle
  • Results service: 5 Twirp routes (step logs, job logs, step summaries, workflow steps, signed blob URLs)
  • Timeline: PATCH updates with lastModified stamps, GET for full history
  • OIDC: RS256-signed JWTs, X.509 chain, JWKS endpoint, OpenID discovery
  • Cancellation: JobCancelMessage with GUID jobId, graceful + hard-kill phases
  • Location services: 28 service definitions matching the hosted topology

Verified by 24 golden conformance scenarios replayed from official runner v2.336.0 wire captures — all pass on status codes, request body schemas, and acquirejob response schemas.

12 // SUMMARY

act is a pragmatic tool for quickly testing workflows locally. It reimplements the runner in Go and runs steps in Docker. Easy to install, huge community, fine for simple workflows — but it breaks down on advanced features (OIDC, concurrency, permissions) and cannot guarantee behavioral parity because it is a clean-room reimplementation.

preloop reimplements the entire stack — both the server-side control plane and the runner — in Rust. `preloop-runner` is a faithful port of `actions/runner` v2.336.0 handling the full step lifecycle. Both sides in Rust means the full wire protocol is exercised end-to-end and conformance is verified against golden captures: rigorous conformance testing, sub-host-speed performance, a DAP debugger, and full OIDC/concurrency support. More to set up, but much higher fidelity.

The fundamental difference is scope: act reimplements only the runner; preloop implements both the server and the runner with the real wire protocol between them. This single decision cascades through every other difference in the comparison.
