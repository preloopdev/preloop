What Problem Does aksh Solve?

GitHub Actions workflows are defined in YAML, but running them locally has always been a lie.

🚫

Docker ≠ GitHub

Most "local GHA" tools run steps in Docker. But GitHub Actions uses a runner that speaks a real protocol with encrypted messages, timeline records, annotations, OIDC tokens, and service endpoints. Docker doesn't model any of that.

🔗

runner.server Exists — But It's C#

ChristopherHX/runner.server proved this works: a local server that the official runner talks to. It works. But it's a .NET app with a 104MB footprint.

🦀

aksh: Same Protocol, Rust Speed

aksh reimplements the control plane in Rust — 4.7MB binary, 8ms startup, 37K req/s. Same protocol fidelity, plus pluggable backends for any runner host (containers, VMs, microVMs, bare processes).

The Core Insight: Control Plane ≠ Execution Engine

The runner protocol already separates "what to run" from "how to run it."

The official actions/runner is the execution engine. It boots, registers with a server, long-polls for jobs, receives an encrypted message containing everything it needs, executes steps, and streams results back. The server never reaches out to execute anything.

This means aksh's only job is to be a faithful server. It doesn't care whether runners live in containers, VMs, microVMs, or bare processes. The runner connects in; aksh feeds it jobs.

Design principle: Model the Azure DevOps wire protocol as the source of truth. Layer aksh-specific features (NDJSON, secret redaction, agent-friendly REST) as read-model projections — never as protocol replacements.

Step by step

1. Submission

Workflow arrives

A CLI, agent, or API submits POST /api/v1/runs with the YAML workflow, event name, payload, secrets, and optional reusable workflow YAML. aksh parses it, checks the trigger matches, expands the matrix, and queues expanded jobs.

2. Runner Registration

Runner connects and authenticates

The runner first calls GET /_apis/connectionData to discover service endpoints. It registers via POST /_apis/.../agents (sending its RSA public key), then creates an encrypted session via POST /_apis/.../sessions — aksh generates a random AES key and RSA-wraps it for the runner.

3. Job Delivery

Encrypted message via long-poll

The runner long-polls GET /_apis/.../messages?sessionId&lastMessageId. When a job is ready, aksh builds a fully-resolved AgentJobRequestMessage (all ${{ }} expressions evaluated, variables materialized, secrets masked, maskHints set, service endpoints attached), AES-encrypts the body, wraps it in a TaskAgentMessage, and delivers it. The runner decrypts with its session key and starts executing.

4. Execution Feedback

Timeline, logs, annotations stream back

As steps run, the runner PATCHes TimelineRecords (step state, result, issues/annotations), creates and appends log files, streams live console lines, and reports job completion with outputs. aksh projects all of this into run state and emits NDJSON events for agents.

5. Completion

Outputs, needs-gating, next jobs

On JobCompleted, aksh persists the job's outputs and updates the run status. The scheduler checks if any downstream jobs' needs are now satisfied, evaluates their if conditions against real job-status functions, and dispatches the next eligible jobs.

6. Cleanup

Ephemeral runner torn down

If the runner was provisioned by an ephemeral provider, aksh tells the provider to terminate it. If BYO, the runner stays. Either way, the run record with all timeline data, logs, and annotations persists.

Pluggable Backends

One control plane. Any execution substrate.

aksh doesn't hardcode how runners are created. It defines a RunnerProvider trait that any backend implements:

pub trait RunnerProvider: Send + Sync {
    /// Labels this provider can satisfy.
    fn labels(&self) -> &LabelMatcher;

    /// Start a runner that phones home via the normal protocol.
    async fn provision(&self, spec: &RunnerSpec, reg: RunnerRegistration)
        -> Result<RunnerHandle, ProviderError>;

    /// Tear down (ephemeral cleanup).
    async fn terminate(&self, handle: &RunnerHandle) -> Result<(), ProviderError>;

    /// Optional capacity for backpressure.
    async fn capacity(&self) -> Capacity { Capacity::unbounded() }
}

The base case is BYO (Bring Your Own) — no provider needed. Self-hosted runners just register and poll. aksh works without any provider crate at all.

⚙️

Process Provider

Spawns a Runner.Listener as a child process. Fastest, least isolation. Good for development.

🐳

Container Provider

Docker or Podman. Each job gets its own container. Good isolation, fast startup.

🖥️

libkrun Provider

MicroVM via libkrun. Hardware-level isolation with sub-second boot. What Preloop uses.

☁️

Cloud / Remote Provider

Kubernetes pods, Firecracker VMs, cloud instances. For server-side use.

Adding a new backend = implement the trait. Zero control-plane edits.

What Makes aksh Different

Beyond just reimplementing runner.server.

📊

NDJSON Agent Feed

A machine-readable event stream derived from timeline records. AI agents can subscribe and react to job status, step completions, annotations — in real time, no polling.

🔒

Redaction-Safe Secrets

SecretString type that can never accidentally log a secret value. Debug, Display, and Serialize all emit <redacted>. Raw access requires explicit .expose().

🧩

Two Protocol Surfaces

The runner-compatible _apis/... surface (source of truth) plus an agent-friendly native REST + NDJSON surface — both reading the same state.

⚡

Small & Fast

4.7MB binary. 8ms startup. 37K req/s. No .NET runtime, no 104MB extraction. Single native process.

🏗️

Crate Boundaries

Separate crates for protocol, parser, expressions, server, client, cache, artifacts, conformance. Each independently testable and replaceable.

✅

Zero Unsafe

unsafe_code = "forbid" at workspace level. All external protocol surfaces versioned with golden fixtures.

Implementation Roadmap

Phased approach — each phase independently testable.

PhaseGoalStatus
A — AzDO Wire DTOs Typed, golden-tested wire models for every protocol message partial
B — connectionData + Auth Runner discovers endpoints and authenticates missing
C — Session Crypto RSA/AES key exchange, encrypted message queue missing
D — Job Message Builder Wire expression evaluator, build AgentJobRequestMessage missing (engine exists, unwired)
E — Timeline + Logs Step status, logs, annotations stream back to server missing
F — needs DAG + Outputs Dependency-gated scheduling, output propagation missing
G — Triggers + Matrix Fidelity Branches/tags/paths matching, declaration-order matrix partial
H — Actions + Cache + Artifacts Action download, cache/artifact v2 blob protocols partial v1

Critical path: A → B → C → D → E = first real runner runs one job. Then F → G → H = any in-scope workflow works exactly like GitHub.

The Name

aksh is the control plane. Preloop is the product.

aksh (this repo)

The GitHub Actions control plane. Reimplements the runner protocol in Rust. Anyone can use it — cargo install aksh — and point their own runners at it. Execution-agnostic.

Preloop (the product)

Combines aksh + a libkrun microVM provider for local CI. The full "submit a workflow, run it in an ephemeral VM, get results" experience. Uses aksh as its control plane.

aksh = the engine. Preloop = the car. You can put the engine in any car.
