## CRITICAL

### PEXP-01 · hashFiles produces wrong cache keys
`crates/aksh-gha-expressions/src/lib.rs:472–490`

Official runner (`hashFiles.ts:29-35`) concatenates **raw binary digests** then SHA-256s them.
aksh formats each digest as a hex string, concatenates those strings, and hashes the UTF-8 bytes.
Different algorithm → different keys. Every `hashFiles()` call will miss cache against real GitHub or
any other conformant runner.

**Fix:** replace `format!("{digest:x}")` / `combined.push_str(...)` with
`combined.extend_from_slice(&digest[..])` using a `Vec<u8>` buffer, then hash that.

---

### RCON-03 · Private registry authentication not implemented
Zero matches for `docker login`, `password-stdin`, `registry_auth` in `crates/aksh-runner/src`.

Container steps pulling from private registries will 401/403 silently. The official runner calls
`docker login` with the `credentials` block from `container:` / `services:`. Whole feature class
is dark.

## HIGH

### RHAND-01 · `github.action` context set to step name instead of step ID
`crates/aksh-runner/src/worker/handlers/action.rs:26–28`

Official `StepsRunner.cs:118` assigns `github.action = actionStep.Action.Name` (step ID, e.g.
`actions/checkout`). aksh uses `ctx.step_name` (display name). Any workflow referencing
`github.action` sees the wrong value.

**Fix:** trivial — use the step ID field instead.

---

### RCON-01 · `docker exec` missing `-i` flag
`crates/aksh-runner/src/worker/container_ops.rs:789`

`build_docker_exec_args` produces `exec -w <workdir> [--env K]... <id> <cmd>` — no `-i`.
Official `DockerCommandManager.cs` always passes `-i`. Without it anything inside the container
that reads stdin hangs or errors.

**Fix:** insert `"-i".into()` after `"exec".into()` in `build_docker_exec_args`.

---

### RCON-02 · Service container health-check backoff is hardcoded linear
`container_ops.rs` — `wait_for_services_healthy` (~lines 462-481)

Official runner uses exponential backoff. aksh polls at a fixed interval — times out sooner than
expected for slow-starting services.

## MEDIUM

### RCMD-01 · Regex recompiled on every log line
`crates/aksh-runner/src/worker/matchers.rs:255, 281`

`Regex::new()` is called inside the hot path once per matcher pattern per output line. On a job
with 10 k lines and 5 matchers × 2 patterns that is 100 k+ regex compilations. Official runner
compiles on registration.

**Fix:** compile at `add_matchers` time, store `Regex` objects in the matcher struct.

---

### RLIS-01 · Message dedup set not scoped to session lifetime
`crates/aksh-runner/src/listener/broker_listener.rs:45–186`

`processed_message_ids: HashSet<i64>` lives for the process lifetime. When the broker session
is recreated (happens on 401/transient error), new server-assigned IDs can collide with old ones
in the set, dropping valid jobs.

**Fix:** clear the set on every session recreate.

---

### RLIS-06 · RSA credential files written world-readable
`crates/aksh-runner/src/settings.rs` — no `set_permissions` / chmod call anywhere.

Official runner chmods `.credentials`, `.credentials_rsaparams`, `.runner` to 0600 on
Linux/macOS. aksh writes them at process umask (typically 0644). On a shared host the private key
is readable by group members.

**Fix:** `std::fs::set_permissions(path, PermissionsExt::from_mode(0o600))` after every
credential file write, gated on `#[cfg(unix)]`.

---

### RLIS-02 · OAuth token refresh is reactive, not proactive
`crates/aksh-runner/src/listener/broker_listener.rs:119, 303` / `oauth.rs:19`

Token is fetched once at startup; re-fetched only on 401 response. `expires_in` is deserialized
but never used to schedule proactive refresh. Results in one failed request per expiry cycle;
rare risk of dropping a job dispatch on a tight expiry window.
