WebSocket Live Log Pipeline

A walkthrough of how aksh-runner pipes live execution output through the control plane to native subscribers using the Database WAL Replication analogy.

💡 The Core Mental Model: DB WAL Replication

Think of the live log pipeline as a database replication system. Below is the mapping from classic DB concepts to our real code components:

1. The WAL Producer

In a database, transactions generate mutation logs which are written to a local memory buffer before syncing to disk.

Real Code: process::invoke capturing output -> enqueuing into LiveLogQueue.

2. The Replication Primary

The primary server receives transaction streams, appends them to its local log book, and broadcasts them to replicas.

Real Code: ws_live_logs endpoint storing lines in per-job Arc-Mutex live_log_lines and broadcasting via live_log_tx.

3. The Read Replicas

Replicas connect, fetch the historical log snapshot to catch up, then subscribe to the live update feed.

Real Code: UI connecting to live_logs_sse, playing the cached snapshot, then forwarding the broadcast stream.

Visual Pipeline Flow

🚀 Runner Pipeline

1. Intercepting Output

process.rs

Process invocations yield stdout/stderr lines asynchronously. Instead of storing them locally first, we attach a callback constructed via live_logs::process_line_callback.

2. Bounded Local Buffer

live_logs.rs

Lines pass through secret masking and are enqueued into LiveLogQueue. To prevent memory allocation runaway, the queue acts as a bounded ring buffer. If it exceeds 1024 queued lines, new lines are dropped to prevent memory exhaustion.

3. Ephemeral WS Sender

live_logs.rs

A background loop polls the queue and aggregates lines into batches (max 100 lines or 250ms timeout). If the server endpoint falls over, the WS sender retries up to 3 times, dropping the connection permanently if failure rate exceeds 50%. This guarantees live logs never block the core execution.

🖥️ Server Pipeline

1. Authenticated Ingest

lib.rs

The runner performs a WebSocket upgrade handshake at /ws/live-logs/:job_id. Axum's middleware validates the bearer token aksh-system-token before upgrading the connection.

2. Thread-Safe WAL & Dispatcher

lib.rs

Incoming WS text frames are parsed as LiveLogFeedLinesWrapper. The server locks a job-specific Arc<Mutex<Vec<...>>>, appends the lines (the WAL snapshot), and sends them to a tokio broadcast sender.

3. Replaying to Replicas (SSE)

lib.rs

When a client hits the Server-Sent Events endpoint, we clone the historical log snapshot from the per-job Mutex, stream it immediately, and then chain the receiver stream. This ensures the client catches up seamlessly without races or duplicate lines.

Where the Database WAL Analogy Diverges

  • Best-Effort vs Strong Durability: In a real database, transaction logs must survive crashes. Live streaming logs are intentionally ephemeral: if a runner loses connection, it will drop live frames rather than backing up local memory or blocking execution. The durable source of truth is still the full step-log blob uploaded to the store at the end of each step.
  • Replication Lag Drops: In database replication, replicas wait or apply backpressure if they lag. If our SSE client lags behind the 1024 channel buffer capacity, the stream is closed or drops events. This keeps server memory footprint strictly bound.
  • Short-Lived WAL: A database retains WAL logs for recovery or backup. The server evicts all memory-buffered live log lines as soon as `completejob` runs, keeping heap memory free.
