Preloop separates workflow interpretation, control-plane coordination, runner protocol handling, and job execution. The diagrams below use the public architecture assets in the repository. For the crate-by-crate map and implementation details, see [Technical architecture](/architecture).

## System overview

The control plane accepts workflow runs, expands them into jobs, and schedules work to runners. Each job executes in an isolated environment; the runner reports logs, status, and results through the runner protocol.

![Preloop system overview](/diagrams/01-system-overview.svg)

## Control plane

The control plane owns run state, job scheduling, authentication, GitHub integration, webhook processing, and result reporting. The native `/api/v1/` surface serves the CLI and agent tools; the `/_apis/` surface is compatible with the official Actions runner protocol.

![Preloop control plane](/diagrams/02-control-plane.svg)

## Runner and job lifecycle

The runner listener receives jobs and starts a worker for each job. The worker prepares the workspace, evaluates steps and conditions, executes actions and scripts, and reports results back to the server.

![Runner listener, worker, and job flow](/diagrams/03-runner-listener-worker.svg)

![Job lifecycle](/diagrams/08-job-lifecycle.svg)

## Workflow parsing and expressions

Preloop normalizes workflow YAML, builds the dependency graph, expands matrices, and evaluates GitHub Actions expressions before dispatching jobs.

![Workflow parser pipeline](/diagrams/04-parser-pipeline.svg)

![Expression engine](/diagrams/05-expression-engine.svg)

## Protocol and execution backends

The protocol layer carries runner messages and job events. The orchestrator connects job scheduling to the configured execution substrate, including local processes, microVMs, or external runners.
