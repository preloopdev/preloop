Architectural Comparison

Three ways to run GitHub Actions locally. One reimplements the runner. Two reimplement the server. Only one reimplements everything.

nektos/act reimplements the runner in Go and executes steps in Docker. agent-ci (RedwoodJS) reimplements the server in TypeScript, launching the official runner binary in Docker containers — with pause-on-failure for AI agents. aksh reimplements both the server and runner in Rust with full wire-protocol fidelity, running on SmolVM microVMs, somac (macOS), and vowin (Windows).

01 — Architecture

Fundamentally different approaches

The single architectural decision — replace the runner vs replace the server — cascades through every feature, limitation, and tradeoff in both projects.

act

nektos/act

Replaces the runner

Monolithic Go reimplementation. Parses workflow YAML, builds a topological plan from the needs DAG, and executes steps inside Docker containers. Each job gets a long-lived container with tail -f /dev/null as entrypoint — steps run via docker exec. The official actions/runner binary is never used.

Replaces the server

aksh

Replaces the server

Full-stack Rust reimplementation — server and runner. The server implements the complete AzDO/GitHub Actions control plane (100+ API routes, broker lifecycle, OIDC, concurrency, Twirp results service). aksh-runner is a faithful Rust port of the official actions/runner v2.336.0 (Listener + Worker), handling the full step lifecycle. The primary execution backend is SmolVM microVMs (Linux & macOS via libkrun), which support running Docker actions inside the VM. Additional backends: somac (ephemeral macOS VMs via Virtualization.framework) and vowin (ephemeral Windows VMs via QEMU). Process and Docker backends also available.

04 — Wire Protocol

act skips the protocol entirely. aksh reimplements the full stack.

This is the deepest architectural divide. act is a monolith that reads YAML and runs Docker commands. aksh speaks the same protocol that GitHub's hosted infrastructure uses.

act — No wire protocol

  • No runner registration
  • No session management
  • No broker lifecycle
  • No timeline updates
  • No results service
  • No OIDC provider
  • No encrypted message queue
  • No location services
  • No cancellation protocol
  • Actions using ACTIONS_RUNTIME_URL must be intercepted

agent-ci — DTU emulation layer

  • AzDO DistributedTask REST (pool/agent/session/message)
  • Timeline/record PATCH updates
  • Log streaming (POST/PATCH)
  • Action download info
  • Cache REST API (reserve/upload/commit/download)
  • Artifact Twirp v4 + Azure Block Blob
  • GitHub REST mirror (registration tokens, compare, tarball)
  • No session encryption
  • No broker lifecycle (acquirejob/renewjob)
  • No OIDC provider
  • No results-service Twirp
  • No concurrency groups

aksh — Full AzDO wire protocol

  • Registration: RSA key exchange, capabilities, labels
  • Session: AES-CBC encrypted queue, renewal, conflict resolution
  • Broker: acquirejob → renewjob → completejob (9 message types)
  • Timeline: PATCH updates with lastModified, GET for history
  • Results: 5 Twirp routes, signed blob URLs
  • OIDC: RS256 JWTs, X.509 chain, JWKS, OpenID discovery
  • Cancellation: GUID + TimeSpan, graceful → hard-kill
  • Location: 28 service definitions, fresh-cache responses
  • Live logs: WebSocket feed + console log API
  • 100+ API routes under /_apis/* and /broker/*

07 — The Bottom Line

Different tools for different problems

act reimplements the runner. agent-ci reimplements the server and uses the official runner. aksh reimplements both — and that's why the fidelity gap between them is what it is.
act

Best for

  • Quick local smoke tests of simple workflows
  • Zero-setup, zero-dependency quick start
  • Visualizing workflow graphs
  • Dry-run / list mode before running
  • Teams already using Docker for development
ash

Best for

  • Full-fidelity local CI matching GitHub's behavior exactly
  • Debugging workflow logic step by step (DAP + pause-on-failure)
  • OIDC token testing
  • Concurrency group testing
  • Full wire-protocol fidelity (server + runner)
  • CI infrastructure (ephemeral runners, runner groups)
  • Performance-critical CI pipelines
  • macOS runners locally (somac)
  • Windows runners locally (vowin)
