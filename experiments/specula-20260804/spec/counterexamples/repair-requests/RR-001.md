## Trigger
Counterexample reaches dispatch (PromoteDispatchJob) without acquiring the job-level concurrency gate for jobs routed through pending_jobs (those with needs: or initial max-parallel violation).

## Evidence
- try_enqueue_with_job_concurrency called only under `needs_empty && under_mp` guard in runs.rs:1096 (see also 1075-1128).
- promote_ready_jobs (runtime_scheduling.rs:977-1048) does direct `inner.queue.extend(promoted)` in Run arm without gate check, on_job_enqueued, or ArriveJobFree trace (cf. lines 14, 76 in try_enqueue).
- TLC CE: SubmitRun2 -> DeclareGate -> EnqueuePending -> PromoteDispatchJob violates GateBeforeDispatch.
- Code comment in try_enqueue_with_job_concurrency acknowledges model/impl path divergence for EnqueuePending + PromoteReadyJob.

## Disposition (verified against preloop source)
CONSUMED — NO SPEC REPAIR APPLIED. The spec is faithful; the violation is a
genuine preloop bug.

Verified chain (2026-08-04):
1. `try_enqueue_with_job_concurrency` has exactly ONE production call site:
   `crates/preloop-runner-server/src/runs.rs:1098`, inside `if needs_empty && under_mp`
   (runs.rs:1099-1121). Jobs with `needs:` (or over max-parallel) never pass
   through the gate evaluator.
2. Such jobs are pushed to `inner.pending_jobs` (runs.rs:1118) with
   `queued_job.concurrency` still set, then `promote_ready_jobs`'s Run arm
   (runtime_scheduling.rs:850-857) pushes them straight into `inner.queue` —
   no `queued_job.concurrency` reference anywhere in the promote loop.
3. `take_matching_job` (runtime_scheduling.rs:1032-1060) performs zero
   concurrency checks (verified: 0 matches for concurrency/try_acquire in its
   body).
4. The only job-level gate acquisition path is submit-time
   `try_enqueue_with_job_concurrency`; `concurrency_blocked` (the park queue)
   is populated exclusively by that function, so needs-gated jobs never enter it.
5. GitHub Actions semantics: job `concurrency:` applies when the job starts,
   regardless of `needs:`. The promote-path bypass is a real divergence.

Therefore the model action `PromoteDispatchJob` (no gate check) faithfully
mirrors the code; the correct fix is in the Rust code (move gate evaluation to
the promote path), NOT in the TLA+ model. The finding MC-S3-job-gate-bypass
stands as a confirmed bug.
