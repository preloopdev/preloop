# Taste (Continuously Learned by [CommandCode][cmd])
- Prefers story-style, narrative explanations when learning about complex systems — not dry technical docs. Confidence: 0.85
- Wants explanations aimed at a total beginner's level, assuming no prior project context. Confidence: 0.85
- Values depth and thoroughness: wants to "understand every single part," not surface-level summaries. Confidence: 0.8
- Probes for design limitations, edge cases, and real-world usability gaps — not just how a system works but where it breaks down and what the user-experience tradeoffs are. Frames questions from an end-user perspective ("so as a user if my agent is debugging..."). Confidence: 0.75
- Cares about clean separation between proprietary/internal features and standard-compatible behavior — wants to know that custom mechanisms are properly gated and won't leak into standard protocol paths (e.g., "what if I want to use the Axe runner against GitHub? Is it going to do the same thing, which we don't want?"). Confidence: 0.7
- Cares about polished, high-quality design output; explicitly invokes the "impeccable" design skill for visual deliverables. Confidence: 0.8
- Prefers editorial long-form aesthetic: warm-tinted paper/light background, serif display + clean grotesque body text, monospace for code/paths. Reads like a beautifully designed long-form essay (Stripe Press / Increment style). Confidence: 0.75
- Does not want generic "AI-slop" aesthetics (neon-on-dark, purple gradients, glass cards). Confidence: 0.7
- Uses `cloudflared` quick tunnels to expose local content publicly. When asked to "expose" something, expects a cloudflared tunnel. Confidence: 0.8
- Prefers PNG exports for documentation diagrams; wants to remove excalidraw source files and SVGs from the repo, keeping only the rendered PNGs. Confidence: 0.6
- Expects the assistant to work autonomously to completion without pausing for confirmation mid-task; repeatedly uses short continuation prompts ("continue", "continue and finish", "can u finish this") when the assistant stops partway. Confidence: 0.8
- Uses casual, terse messaging style ("can u finish this", "continue and finish") — informal and brief rather than fully spelled-out requests. Confidence: 0.75
- Prefers pragmatic, minimal solutions over over-engineered features: when a simpler change achieves the goal (e.g., always granting all capabilities vs. building a dynamic update endpoint), the user agrees with and expects the simpler path. Confidence: 0.7
- Prefers scoping plans, architecture documents, and deliverables to the immediate target rather than building for all future scenarios at once. Keeps future extensibility as brief notes, not full detail ("the initial focus will be on local CI"). Confidence: 0.7
- When scope or content changes, expects all related artifacts (e.g., source markdown plan and derived HTML explainer) to be updated together to stay in sync. Confidence: 0.65
- When asking for a walkthrough of a large code change, wants it organized by area/component — each section explaining what it tests or covers and why it matters, so they get a mental map of the change's scope before any deep dive. Confidence: 0.75
- When committing changes, wants modified/tracked files committed but untracked (new) files left out for personal review before they enter version control. Confidence: 0.85
- Prefers changes broken into multiple logical, atomic commits organized by component or concern area rather than one large monolithic commit. Confidence: 0.75
- Wants conventional commit prefixes (feat, fix, chore, docs, test, etc.) to accurately reflect the nature of each change — will request amendments if categories are mislabeled. Confidence: 0.8
- Prefers dense technical plans and architecture documents transformed into polished, navigable HTML explainer pages rather than reading raw markdown. Wants interactive elements when they help explain concepts — scenario tab switchers, step-through flow simulators, expandable taxonomy rows, live key builders — not just static text. Explicitly asks to "be creative" with how concepts are visualized. Confidence: 0.75
- Pivots quickly mid-conversation ("actually never mind, can u give me...") and expects the assistant to immediately adapt and pursue the new direction without friction or pushback. Confidence: 0.6
- Wants honest, clear reporting of what was actually accomplished vs. what was only attempted or analyzed — will call out when a summary overstates results (e.g., presenting code analysis as if real profiling was done). Distinguishes between "I ran benchmarks" and "I read the code." Confidence: 0.85
- Values actual execution and empirical measurement over code analysis presented as performance findings — wants real workloads run through the system and real numbers, not structural code review dressed up as profiling results. Confidence: 0.8
- Has deep knowledge of their own system architecture and will push back on claims that conflict with how things should work — expects the assistant to investigate root causes of failures before reporting symptoms (e.g., "Node 24 is missing" should have prompted "why is it missing if it's baked into the golden?" before being reported as a blocker). Confidence: 0.7
- Expects the assistant to attempt to access, inspect, or run something directly before claiming it can't be done — don't prematurely assert limitations ("I can't inspect the golden VM") when the tools to do so are available. The user will call out unjustified "can't" statements. Confidence: 0.8
- Questions redundant runtime work as a design smell — expects dependencies to be pre-baked into golden/base images rather than reinstalled on each run. Frames this as an obvious efficiency expectation ("why are we reinstalling everytime and not just baking it into the golden"). Confidence: 0.7
- Follows an instrument-before-optimize methodology: explicitly states "Phase 0: Instrument before changing policy" and "Do not optimize a phase that cannot be separately measured." Wants measurement infrastructure built and baselines established before any performance changes are made. Confidence: 0.8
- Wants benchmark/profiling output as structured, comparable JSON records with per-phase metrics (not aggregates), categorized outcome reasons (e.g., cache hit/miss), and byte-level + latency accounting. Expects benchmarks run across multiple varied workloads for meaningful coverage. Confidence: 0.75
- Expects empirical results to be synthesized into actionable "so what does this tell us?" analysis — not just raw data tables, but strategic interpretation: what's the actual bottleneck, what should we do about it, what should we NOT bother optimizing. Wants the assistant to extract meaning and concrete recommendations from data. Confidence: 0.8
